## 未完成 / 未验证项（如实声明）


1. **53 来源/67 项完整覆盖未验证**：召回验证只证明「库可检索」，42/70 直接匹配 + 14 别名映射 ≠ 全量病例正文可取。尚需按 72 项清单逐项核验「正文可取 / 媒体可取 / 训练可用」三态并记录证据。教师审核结构化导入的最小方案已产出（`docs/教师审核导入方案.md`），**批量导入未实施**（需真实教师逐例审核）。
2. ~~快照持久化未实现~~ **已实现（2026-10-08/09 核验更新）**：`case_snapshot_facts/answers` 双表持久缓存 + 会话绑定 `sourceSnapshotVersion`；重启后按固定版本恢复教学事实（restore RPC + 版本校验）。多患者混拍风险仍部分存在（见第 3 条）。
3. **多患者混拍风险未消除**：召回按「病例名」匹配，同名病种多个住院记录可能混合；当前无「精确来源文档 ID + 同一患者记录匹配」校验。缺失必填事实时保持「资料不足」，未默认年龄/性别/体征（已实现）但完整性与出处逐项校验未实现。教师审核固定版本（导入方案）可根治此风险。
4. **SDK 全文/文件获取能力——已核验，不支持**（2026-10-08 实测）：`KnowledgeClient` 仅暴露 `recall`（返回分片的 `title`/`content` 两字段，**无文档 ID**）与 `list`（仅知识库元数据：id/baseName/description/creator 等）。SDK 无按文档 ID 获取全文、无文件下载接口。因此 topK 多查询召回是唯一获取途径，**这不等于全文导出**：影像册分片可能被截断、正文分片顺序不保证。当前缓解：多查询变体（4 个）+ sha256 去重 + 分段解析；根治需平台侧提供「按文档 ID 取全文」能力。召回阈值当前 0.2，不再通过继续调低阈值宣称提升覆盖率。
5. **3 系统完整训练流程未验收**：启动→问诊→查体→检查→诊断→报告 的完整链路仅做过单点验证（问诊/查体/辅检各一次 200），未做 3 个不同系统病例的全流程记录。
