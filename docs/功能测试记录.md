## 0. 测试说明与方法

### 0.1 测试对象
- **线上系统**：`https://tbm8rhj8mq.coze.site/`（Coze 部署环境）
- **技术栈**：Next.js 16（App Router）+ React 19 + Tailwind v4 + Supabase + coze-coding-dev-sdk
- **核心业务**：面向武汉大学儿科学教学的统一儿科教学智能体，贯穿「问诊 → 查体 → 辅助检查 → 诊断处置 → 沟通 → OSCE → 学情分析」全链路。

### 0.2 测试方法
由于系统采用**超星 OAuth 鉴权**，受保护路由在未登录态下由服务端（SSR）直接返回落地页（landing），无法在测试环境内完成全链路真人点击。因此本记录采用**三层印证法**：

1. **线上公开路由实测**：对无需登录的公开页（首页 `/`、关于页 `/about`）进行真实访问与截图。
2. **源码实现审查**：对 `src/app/**`、`src/components/**`、`src/domain/**` 逐模块审查，还原真实交互逻辑与状态机。
3. **路由探测**：通过页面产物与源码确认全部路由与入参约束。

> 说明：凡标注「源码推断」的流程，均已在 `src/domain/agent.ts`、`src/components/training-workspace.tsx` 等核心文件中核实；标注「线上实测」的，已有真实截图佐证的（`output/live-test/01-home.png` 等）。

## 1. 逐模块测试记录

### 模块 1 · 登录落地页（`/`）
- **操作流程**：打开根域名 → 展示珞珈印章 + ECG 心电动画 + 产品主张 → 点击「进入守护营 / 超星登录」→ 跳转超星 OAuth 授权。
- **交互逻辑**：纯展示 + 单一 CTA；ECG 动画为装饰性氛围元素；落地页同时承担「未登录访问受保护路由时的 SSR 兜底页」。
- **用户痛点**：
  1. 受保护路由（如 `/student`）在未登录时被 SSR 重定向回落地页，但**没有任何「请先登录」的提示或登录入口高亮**，用户容易误以为页面「坏了」。
  2. 游客体验入口不明显，首次来访者缺乏「先看看能做什么」的低门槛路径。
- **使用场景**：学生/教师首次访问、分享链接被未登录用户点开、 OAuth 回调后落地。

### 模块 2 · 超星 OAuth 登录（`/auth` 流程）
- **操作流程**：落地页 CTA → 发起授权（`CHAOXING_REDIRECT_URI`）→ 超星回调 → 用户创建/绑定（虚拟邮箱 SHA-256）→ 角色权限映射（教师白名单 `CHAOXING_TEACHER_UIDS`）→ HttpOnly Cookie + 签名登录上下文 → 进入对应首页。
- **交互逻辑**：AppSecret 仅服务端；登录态以签名 Cookie 保存；学生/教师角色由白名单决定，空白名单 = 全部学生权限。
- **用户痛点**：
  1. 回调地址必须与超星后台**逐字符一致**，配置错位会静默失败，错误页信息晦涩。
  2. 登录失败（如超星拒绝、网络超时）缺乏明确的「重试 / 联系管理员」引导。
- **使用场景**：每学期首次开课批量登录、教师首次获得后台权限、回调域名变更后回归验证。

### 模块 3 · 学生首页（`/student`）
- **操作流程**：登录 → hero 欢迎区（等级/连续天数）→ 病例库入口 → 三个核心入口（训练 / 练习 / OSCE）→ 六维能力条。
- **交互逻辑**：首页是「门户」而非「工作台」，所有训练动作都从三个入口分发；能力条为只读概览。
- **用户痛点**：
  1. 首页信息密度偏高，旗舰病例与三个入口 + 能力条 + 病例网格同屏，移动端首屏压力大。
  2. 「下一步该做什么」缺乏显式引导（无「继续上次」「推荐病例」）。
- **使用场景**：学生每日登录开始学习、教师演示产品、期中/期末集中训练。

### 模块 4 · 病例库（`/student` 内嵌）
- **操作流程**：首页进入病例库 → 浏览病例卡（含难度/时长/状态标签）→ 筛选或搜索 → 选择病例 → 进入训练台。
- **交互逻辑**：当前仅 `peds-respiratory-001`（小宇，发热咳嗽）、`peds-wheeze-002`（小宁，喘息）两个病例；卡片展示解锁/通关状态。
- **用户痛点**：
  1. 病例数量少，且无「按系统/按难度/按能力短板」的智能推荐。
  2. 病例卡信息维度单一，难以一眼判断「这个病例练什么能力」。
- **使用场景**：学生自选病例、教师布置指定病例前的预览。

### 模块 5 · 沉浸式训练台（`/student/training`）— 核心模块
- **操作流程**：选病例 → 进入 8 阶段训练：
  `triage（分诊）→ history（问诊）→ exam（查体）→ tests（辅助检查）→ assessment（诊断）→ plan（处置方案）→ communication（沟通）→ report（报告）`
  每阶段由智能体驱动对话 + 表单 + 查体热区，阶段结束 `NAVIGATE_STAGE` 推进。
- **交互逻辑**（源码 `src/components/training-workspace.tsx` + `src/domain/agent.ts`）：
  - 患儿以 **SVG 头像 + 体征热区**呈现，可点击身体部位触发查体（`EXAM_ACTION`）。
  - 问诊阶段学生以**对话气泡**与患儿/家长互动（`ASK_QUESTION` / `DOCTOR_INTERVENTION`）。
  - 辅助检查阶段从器材栏**开单**（`ORDER_TEST`）。
  - 诊断/处置阶段提交结构化决策（`SUBMIT_DECISION` / `SUBMIT_PLAN`）。
  - 沟通阶段生成面向家长的话术（`SEND_COMMUNICATION`）。
  - 全程由确定性临床规则 + 可选模型兜底评分，产出 `TrainingReport`（六维能力 + 证据 `ScoreEvidence`）。
- **用户痛点（高优先级）**：
  1. **问诊被做成「选择题」**：原交互以预设选项为主，学生无法像真实医生一样**自主组织语言询问**，违背「临床思维训练」本质。
  2. **缺乏实时引导**：学生在 open-ended 问诊时容易「不知道问什么」，缺少按需出现的「AI 提示」 scaffolding。
  3. 8 阶段连续无显式「保存/退出/续接」提示，中途离开成本高。
  4. 查体热区缺乏「已查 / 未查」的清晰状态反馈。
- **使用场景**：日常临床推理训练、考前专项突破、教师示范带教。

### 模块 6 · 专项练习（`/student/practice`）
- **操作流程**：进入练习 → 复用训练台能力，但聚焦单一能力维度（如仅问诊、仅查体）的短闭环练习。
- **交互逻辑**：源码中与训练台共用 `training-workspace`，通过 `mode: 'practice'` 区分，去除了完整 8 阶段，强调单点强化。
- **用户痛点**：
  1. 与训练台界面高度同源，**缺乏「练习 vs 训练」的视觉区分**，学生不清楚差异。
  2. 练习结果未与短板诊断打通（练完不知道下一题该练什么）。
- **使用场景**：针对某次报告暴露的弱项（如「沟通」得分低）做靶向练习。

### 模块 7 · OSCE 考站（`/student/osce`）
- **操作流程**：进入考站 → 阅读考站规则 → 一次性开始（限时倒计时）→ 完成考核 → 自动提交 → 生成可解释评分报告。
- **交互逻辑**（`mode: 'osce'`）：限时 `expiresAt` 驱动；**全程无教学提示**；结束 `FINISH_SESSION` 自动交卷；评分可解释（附证据）。
- **用户痛点**：
  1. 限时压力大，开始前缺乏「模拟演练 / 规则确认」缓冲。
  2. 规则以纯文本罗列，关键信息（限时自动提交、异常不丢记录）易被忽略。
- **使用场景**：期中/期末标准化考核、执医 OSCE 模拟。

### 模块 8 · 报告列表（`/student/reports`）
- **操作流程**：进入 → 按时间/分数浏览历史报告卡（病例名 + 总分 + 日期 + 模式标签）→ 点击查看详情。
- **交互逻辑**：报告由 `TrainingReport` 渲染；列表为只读摘要。
- **用户痛点**：
  1. 缺乏「进步趋势」线，学生只看单点分数，难感知成长曲线。
  2. 报告与病例/练习之间缺少回链（看到低分无法直接「去补练」）。
- **使用场景**：阶段性自评、考前复盘。

### 模块 9 · 报告详情（`/student/reports/[id]`）
- **操作流程**：列表点入 → hero（病例/总分/模式）→ 六维能力雷达/条形 → 证据卡（每项得分 + 达成/未达成 + 说明）→ 优势/待改进/建议 → 一键「补练」入口。
- **交互逻辑**：`abilities`（六维）+ `evidence`（证据项）+ `strengths/improvements/recommendation` 全量展示。
- **用户痛点**：
  1. 六维能力的「为什么得这个分」需要点开证据卡，**首屏看不到归因**。
  2. 「建议」与「补练」之间断层，建议未自动转化为可执行的练习任务。
- **使用场景**：教师讲评依据、学生深度复盘。

### 模块 10 · 教师学情台（`/teacher`）
- **操作流程**：教师登录 → 顶部统计（班级人数/平均分段/活跃度）→ 学生搜索/筛选 → 学生卡（姓名 + 概览 + 最近报告）→ 进入会话详情。
- **交互逻辑**：**只读**学情聚合；权限由 `CHAOXING_TEACHER_UIDS` 控制；数据来自 Supabase 同步。
- **用户痛点**：
  1. 班级维度统计后**缺少「群体共性短板」洞察**（如「本班沟通题普遍低」）。
  2. 学生卡信息粒度不足以快速定位「谁需要干预」。
- **使用场景**：教师每周学情巡检、考前班级画像、个别化辅导决策。

### 模块 11 · 教师会话详情（`/teacher/sessions/[id]`）
- **操作流程**：学情台点学生 → 查看其单次会话全过程（阶段轨迹 + 对话 + 证据 + 评分）→ 可导出/批注。
- **交互逻辑**：基于 `SessionState` 全量回放；`status: 'pending_review'` 可进入复核。
- **用户痛点**：回放信息量大，**缺少「一键定位失分关键节点」**的跳转。
- **使用场景**：教师对争议评分复核、典型案例课堂讲解。

### 模块 12 · 智能体说明（`/about`）— 线上实测
- **操作流程**：公开可访问 → 介绍智能体能力、教学理念、数据合规。
- **交互逻辑**：静态说明页，无需登录（截图 `02-about.png` 实测为极小占位，疑似 SSR 兜底）。
- **用户痛点**：说明页与产品实际能力**存在信息差**，新用户无法快速建立「这东西怎么帮我学」的认知。
- **使用场景**：参赛者/评审了解项目、学生了解智能体边界。

### 模块 13 · 登录错误页（`/auth/error`）
- **操作流程**：OAuth 失败 → 展示错误码/信息 → 提供重试或返回。
- **交互逻辑**：读取 `?error=` 参数渲染；`ApiError{code,message,retryable}` 决定按钮。
- **用户痛点**：错误描述偏技术化，学生看不懂；重试入口有时会回到同一条失败链路。
- **使用场景**：超星拒绝授权、会话过期、网络抖动。

## 2. 跨模块痛点汇总（按严重度）

| 严重度 | 痛点 | 涉及模块 | 设计侧对应优化 |
|--------|------|----------|----------------|
| 🔴 高 | 问诊做成选择题，违背临床思维训练 | 5 | 改为自由输入 + 「AI 提示」按钮 |
| 🔴 高 | 受保护路由无登录提示，误以为页面坏 | 1、2、13 | 落地页增加登录态感知与引导 |
| 🟠 中 | 报告建议未转化为可执行补练 | 8、9、6 | 报告详情「补练」直链专项练习 |

| 🟠 中 | 练习与训练视觉无区分 | 5、6 | 模式化色彩/标签区分 |
| 🟡 低 | 首页首屏密度过高 | 3 | 旗舰卡情境化、信息分层 |
| 🟡 低 | OSCE 规则易被忽略 | 7 | 规则卡视觉强化 + 演练缓冲 |

## 3. 测试结论

1. **业务闭环完整**：8 阶段临床流程 + 六维能力画像 + 证据化评分 + 教师只读学情，链路自洽，符合儿科教学智能体的定位。
2. **最大体验风险在「问诊的交互真实性」与「登录态的引导缺失」**——前者是教学有效性核心，后者是转化漏斗第一关，均为高优先级优化项。
3. **数据资产已就绪**：`SessionState` / `TrainingReport` / `ScoreEvidence` 结构成熟，足以支撑更丰富的学情可视化（趋势、群体、归因）。
4. **设计稿已覆盖全部 13 模块**中的核心 10 屏（见设计优化说明文档的「画布屏映射」），专项练习/智能体说明/登录错误三屏需在最终稿内补齐（已在交付排期中）。
