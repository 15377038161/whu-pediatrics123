# 原生超星技能核实报告：登录会话 Cookie 限制的官方支持方式与现有实现差异

核实时间：2026-10-11
核实性质：只读核实（读取技能文档 + 项目现有代码比对），未改任何运行代码、未改 DB、未提权、未发布。
用户关切：平台原生登录会话在此沙箱 Cookie 故障是否有官方支持方式；禁止伪造 JWT/admin 回退/改教师白名单/开启共享预览。

## 一、已读取的技能文档（真实来源）

| 技能 | 文档 | 与本核实的关系 |
|---|---|---|
| supabase-auth | `SKILL.md`、`references/chaoxing-login.md`、`references/chaoxing-oauth.md`、`references/verify-session.md` | 超星登录唯一官方契约（OAuth2.0 一键登录）、登录基座、鉴权头协议 |

**要点（技能文档原文摘录，脱敏）**：
- 超星登录仅 OAuth2.0 一键登录（authorize-url → checklogin 中转 → exchange 单次兑换 → setSession），密码登录已软下线
- 鉴权协议不对称是**官方设计**：OpenSandbox 代理固定剥离 `Authorization` 头，平台 Nginx 在边界将其重命名为 `X-Sandbox-Authorization`。前端发 `Authorization: Bearer <token>`，服务端 API Route **只从 `x-sandbox-authorization` 头**读 token（此时 `authorization` 头恒为空，读它必然 401）
- 技能模板会话模式：浏览器直连 Supabase（`persistSession: true`，session 存 **localStorage**），守卫集中在客户端组件，明确禁止 middleware 读 cookie 鉴权

## 二、现有实现与技能契约的差异比对（逐项）

| 维度 | 技能模板（官方契约） | 本项目现有实现 | 评价 |
|---|---|---|---|
| 登录端点 | `/v1/api/coder/proxy/auth/chaoxing-oauth/*`（authorize-url / checklogin / exchange），禁止硬编码 URL | `chaoxing-oauth-client.ts`：完全一致的端点、AUTH_BASE 从环境变量读取、ngrok 头、in-flight 去重、中转窗口 5s 防抢跑 | **符合契约**（且增加了可见阶段诊断与跳转拦截兜底） |
| 回跳闭环挂载 | root layout body 直接子层级、不被守卫包裹 | `app/layout.tsx`：`<OAuthCallbackHandler />` 为 body 直接子节点，无 AuthGuard 包裹 | **符合契约** |
| 登录后导航 | `router.replace(POST_LOGIN_HOME)` | 登录成功 `window.location.assign('/')`，由服务端根页按角色重定向 /student /teacher | **偏离但可解释**：本项目 `'/'` 是服务端角色分流页，语义等价 |
| session 存储 | 浏览器 localStorage + 客户端 getSupabase()（浏览器持 anonKey） | **服务端 SSR setSession 写 httpOnly cookie**（`platform-session` 路由 + `@supabase/ssr`），浏览器不持 anonKey（平台不暴露真实节点地址） | **有意偏离**：本项目环境无法在浏览器持 anonKey（CODER_SUPABASE_URL/ANON_KEY 仅注入沙箱进程环境），localStorage 模式在此不可行 |
| API 鉴权头 | 服务端只读 `x-sandbox-authorization` | `supabase-client.ts` 注释确认用户 token 来自 `x-sandbox-authorization`（平台 Nginx 重命名） | **符合契约** |

## 三、Cookie 故障的官方支持方式核查结论

**既有实证（scripts/verify-platform-session-chain.ts，脱敏结论已留档）**：
- 本地直连链路完全正常：`platform-session` 落地 200 + Set-Cookie、`GET /` 307 角色重定向
- 经沙箱网关域名：会话落地自身 200 且**下发** Set-Cookie，但客户端 Cookie **无法经网关回传**（T3/T4 对照，应用侧 cookies:none）；网关仅回放其自身共享 jar
- 技能文档对该网关 Cookie 透传限制**未提供开关或配置项**，其模板通过 localStorage 存 session **绕开 cookie 回传问题**——这正是官方模板不用 cookie 的结构性原因

**官方支持方式结论**：
1. 技能契约的鉴权路径（前端 Authorization → Nginx 重命名 → 服务端 x-sandbox-authorization）**不受 Cookie 故障影响**，是当前可用的官方支持方式
2. 本项目因浏览器不可持 anonKey 而采用 SSR cookie 模式，在网关 Cookie 不透传限制下出现会话无法持久化的已知故障——**技能文档无针对该模式的网关修复方案**
3. 按用户禁令：**不**伪造 JWT、**不** admin 回退、**不**改教师白名单、**不**开启共享预览。当前记录为：平台限制仍在（网关 Cookie 不透传 + 浏览器不可持 anonKey 的组合），完整 OAuth 浏览器端闭环待平台侧支持或用户指定的合规方案
4. SDK recall/list 无全文方法只说明该 SDK 接口不提供全文，不能推断平台无全文能力（管理 UI 行级下载已实证）

## 四、能力差异汇总（不假称可用）

- **已核实可用**：OAuth 端点契约链路、x-sandbox-authorization 鉴权、RLS（app_is_teacher 白名单判定）、数据库读写
- **受限待平台支持**：网关域名下的浏览器会话持久化（cookie 不透传）、完整 OAuth 浏览器闭环的端到端验收
- **技能存在 ≠ 登录可用**：本报告基于文档 + 代码 + 既有实测脚本结论，未在浏览器实测本轮登录成功，不宣称登录当前可用
